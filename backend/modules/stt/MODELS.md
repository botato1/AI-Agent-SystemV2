# STT 모듈 모델 현황

**기준일: 2026-08-07** / 실행 환경: NAS GPU 서버 (aarch64 + CUDA, float16)

파이프라인에 모델이 여섯 종류 물려 있고, 어느 게 어디서 도는지 헷갈리기 쉬워서
한 장으로 정리한다. 숫자는 전부 실측이고 출처를 같이 적었다.

## 2. 음성 인식 엔진

### 왜 Qwen인가 (2026-08-07 유저 결정)

| 엔진 | 일반 회의 음성<br>(AI-Hub held-out 500건) | 우리 회의<br>(대본 대조) |
|---|---|---|
| **Qwen3-ASR-1.7B** ← 현재 | 9.14% | **5.91%** |
| Whisper large-v3 | **7.27%** | 9.21% |

**일반 음성만 보면 Whisper가 1.9%p 낫다.** 그럼에도 Qwen을 쓰는 이유는 우리 조건에서
3.3%p 이득이고, 엔진을 바꾸면 화자 판정·용어·신뢰도 문턱이 전부 엮여 재검증 비용이
크기 때문. **바꾸자는 얘기가 다시 나오면 이 표가 근거다.**

Qwen을 고른 실질적 이유는 **컨텍스트 바이어싱**이다. 팀 용어 목록을 시스템 메시지로
주입할 수 있고(학습된 기능), 우리 녹음 40건 실측에서 66개 목록으로
**용어 재현율 85.5% → 92.8%, CER 7.46% → 5.62%**, 속도 변화 없음.

### 모델 두 개를 쓰는 이유

- **0.6B (fast)** — 1초 주기 partial 스트리밍용. 발화자가 안 쉬어도 화면에 텍스트가
  흐르게 하는 용도라 지연이 전부다. `FAST_BEAM_SIZE = 1` (greedy에 가깝게)
- **1.7B (precise)** — 확정 전사. 회의 중 청크 확정과 종료 후 재분석에 모두 쓴다

### ⚠️ 주석과 실제 기본값이 어긋난 곳

`process_chunk()`의 주석은 "회의 중 자막은 응답성이 중요하니 빠른 모델을 쓴다"고
말하지만, `REALTIME_FINAL_USES_FAST_MODEL` 기본값이 `0`이라 **실제로는 확정 전사도
1.7B를 쓴다.** 정확도 우선으로 켜둔 상태이고 지금 지연에 문제가 없어서 그대로 두지만,
읽는 사람이 헷갈리므로 여기 적어둔다.

### 엔진 전환

`STT_ENGINE=faster_whisper|transformers|qwen` 환경변수로 바꾼다. 미지정이면 CUDA
환경에서 `qwen`으로 붙는다.

**⚠️ 엔진마다 신뢰도 분포가 달라 문턱을 공유할 수 없다.** Qwen은 `avg_logprob` 중앙값이
-0.03, Whisper는 훨씬 아래다. 그래서 `CONF_AVG_LOGPROB_THRESHOLD`가 엔진별로 갈린다
(Qwen: -0.11, 분포 p05 기준). **엔진을 바꾸면 이 값부터 다시 재야 한다.**
또 Qwen은 `no_speech_prob`를 아예 내지 않아 항상 0.0이고, ITN도 적용하지 않아
숫자를 발음형으로 출력한다("8002번" → "팔천이번"). 숫자 표기는
`utils/korean_itn.py` 후처리가 담당한다.

## 3. 화자 관련

### 화자 분리 — `pyannote/speaker-diarization-3.1`

종료 후 재분석에서 "언제 누가 말했나"의 구간을 잡는다. **최소 화자 수를 2로 강제**한다 —
1을 허용하면 pyannote가 "전원 동일인"이라는 결론을 낼 자유가 생기고, 2인 대화 125초
실측에서 실제로 그렇게 무너졌다.

### 화자 임베딩 — `pyannote/wespeaker-voxceleb-resnet34-LM`

목소리 지문을 뽑아 등록된 프로필과 대조한다. 구형 `pyannote/embedding`으로는 임계값을
0.75→0.5로 낮춰도 분간이 안 돼서, 화자분리 3.1이 내부적으로 쓰는 이 ResNet 모델로
교체했다.

**판정 방식이 두 갈래인 게 핵심이다:**

| 상황 | 방식 | 값 |
|---|---|---|
| 참석자를 아는 회의 (닫힌 집합) | 순위 1등 + 2등과의 격차 | `SPEAKER_MIN_MARGIN = 0.05` |
| 명단 밖 사람 방어 | 절대 하한 | `SPEAKER_ABSOLUTE_FLOOR = 0.35` |
| 자동 감지 (열린 집합) | 절대 문턱 | `SPEAKER_MIN_ASSIGN_SIMILARITY = 0.4` |

절대 문턱 하나로 판정하던 게 오배정의 원인이었다. 참석자가 정해진 회의에서는
"0.4를 넘느냐"가 아니라 **"후보 중 누가 제일 가까우냐 + 2등과 충분히 벌어졌느냐"**가
맞는 질문이다.

> ⚠️ `SPEAKER_ABSOLUTE_FLOOR`를 0.30으로 낮춰봤다가 되돌렸다. A/B에서 맞는 답을
> 되살린 게 아니라 **틀린 이름을 들여보냈다.** 다시 낮추자는 얘기가 나오면 이걸 볼 것.

### 동시 발화 감지 — `pyannote/segmentation-3.0`

**⚠️ 인공 겹침으로만 검증됐다(재현율 89%). 실제 회의에서 잡는다는 보장이 아니다** —
같은 방에서 두 사람이 말하면 반사와 거리 차로 복잡하게 섞이는데, 파형을 더한 것과는
다르다. 진짜 겹쳐 말한 녹음을 기다리는 중이고, **그건 튜닝용이 아니라 검증용(held-out)으로
쓸 것.**

구현에서 한 번 크게 틀렸던 부분: 이 모델의 출력은 **multilabel(채널=사람)** 과
**powerset(채널=사람 조합)** 두 형태가 있는데, powerset은 **청크마다 클래스 번호가
가리키는 사람이 다르다.** 그래서 청크를 평균 낸 뒤 argmax를 하면 무의미한 값이 나온다
(`skip_aggregation=True`로 청크별 변환을 먼저 한다).

### 음성 분리 — `pyannote/speech-separation-ami-1.0` (꺼짐)

겹친 목소리를 갈라내는 모델. `speechbrain` 미설치로 못 켠다. 겹침 녹음이 오면 함께
판단할 대상.

## 4. 회의록 문맥 교정 — `qwen2.5:14b` (Ollama, 꺼짐)

전사가 틀린 걸 문맥으로 바로잡는 용도다. 노리는 건 이런 것:

> "이전 결정 **반복**하고" → "이전 결정 **번복**하고"

뜻이 정반대로 뒤집히는 오인식이라 모순 감지에 직접 타격을 준다.

**지금 꺼둔 이유:** 동작은 하는데 **문맥으로 없는 말을 지어낸다.** 전사가 조금 틀리는
것보다 내용이 바뀌는 쪽이 훨씬 나쁘다 — 모순 감지가 없던 모순을 만들 수 있다.
`REFINE_LLM_MAX_EDIT_RATIO = 0.35`로 변경 폭을 제한해뒀지만, 회의 표본이 더 쌓인 뒤
다시 판단하기로 했다. **LLM 쪽은 승주 담당이고 Ollama 주소가 필요하다.**

미설정이면 꺼진 채로 동작한다 — LLM 서버가 없는 환경에서도 재분석은 그대로 돌아야 하므로.

## 5. 용어 컨텍스트

목록이 두 개인데 용도가 다르다:

| 파일 | 대상 | 개수 | 왜 따로 |
|---|---|---|---|
| `core/terms.txt` | Whisper `initial_prompt` | 23 | 길수록 프롬프트를 받아적는 사고 + 224토큰 한계 |
| `core/terms_context.txt` | Qwen 시스템 메시지 | 66 | 두 제약이 없어 넓게 담는 게 이득 |

**숫자(포트 번호 등)는 넣지 않는다.** Whisper에서 없는 숫자로 끌려가는 게 실측됐고,
Qwen도 컨텍스트로 출력 형식을 제어하지 못한다.

**늘릴 때 규칙:** 실측으로 오인식이 확인된 것만 넣고, `finetune/stt/benchmark.py
--compare-terms`로 일반 음성 회귀를 함께 확인한다. 현재 목록의 일반 음성 영향은
**+0.09%p(무해)**로 측정됐다.

## 6. 바꿀 때 반드시 같이 할 것

모델이나 문턱을 건드리면 **일반 성능이 나빠졌는지 반드시 확인한다.**

```bash
python finetune/stt/benchmark.py --manifest finetune/stt/manifest_aihub_heldout.jsonl \
    --meetings <회의ID>:<대본경로>
```

우리 회의만 좋아지고 일반이 나빠졌으면 **과적합이므로 되돌린다.** 목표는 "우리 회의를
잘 인식하는 것"이 아니라 "어떤 회의를 틀어도 잘 인식하는 것"이다.

**⚠️ 단, 재분석 파이프라인(화자 분리·턴 자르기·겹침)은 이 벤치로 확인이 안 된다** —
AI-Hub 셋은 발화 단위 파일이라 그 경로를 안 탄다. 그쪽 변경은 우리 회의 재분석과
코드 근거로만 판단할 수 있고, 그 한계를 알고 써야 한다.
